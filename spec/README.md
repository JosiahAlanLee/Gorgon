# Gorgon specification

This directory is the contract between the pieces of Gorgon. The tracker and
its Python outputs live in [HydraPy](https://github.com/JosiahAlanLee/hydrapy);
the VCV Rack module lives in [`../rack`](../rack). Both implement what is written
here, and the fixture checks that they agree.

| [score-v3.md](score-v3.md) + [score.schema.json](score.schema.json) | Score format 3 (`hydrapy-tracker-3`), part 1: six lanes, 128 patterns and a chain, per-pattern rate, bar and bars, per-lane length, the timeline and its transport changes, and how versions 1 and 2 map onto it | Contract (A-spec-1 of 4, ratified); not implemented |

## What is and isn't the contract

The contract is what crosses a repository boundary: the score, the bridge API,
the signal semantics and the audio port layout. These are **not** part of it,
and each lives with its implementation:

- HydraPy's direct CV and ES-40 configuration (`--cv-device`, `--cv-map`,
  `hydrapy-cv-1` profiles): [es40.md](https://github.com/JosiahAlanLee/hydrapy/blob/main/docs/es40.md).
- The tracker editor's UI, keyboard model and persistence (`.hydrapy/tracker.json`).
- The Rack module's panel, context menu and patch-saved settings:
  [the manual](../rack/docs/MANUAL.md).
- How HydraPy's patches declare scenes and read lane signals (`@scene`,
  `tracker.gate(n)`): [gorgon-tracker.md](https://github.com/JosiahAlanLee/hydrapy/blob/main/docs/gorgon-tracker.md).

## Conformance

[`../rack/tests/fixture.txt`](../rack/tests/fixture.txt) is the reference:
HydraPy's `TrackerCV` evaluated at thousands of beats across random scores,
generated by [`../rack/tools/make_fixture.py`](../rack/tools/make_fixture.py).
`engine_test` checks the C++ engine against it. CI regenerates the fixture from
the HydraPy commit in [`../hydrapy.pin`](../hydrapy.pin) and fails if the
checked-in file differs, so a semantic change on either side is caught.

The browser audition synth in the tracker editor is a third implementation of
the same semantics. It is checked by HydraPy's Chromium tests, not by the fixture.

## Versioning

- The score's `format` string is its version. Adding an optional field with a
  default that reproduces the old behaviour (as `scenes` was added) keeps the
  version. Removing a field, changing a range, or changing what an existing
  field means requires a new format string, and both implementations must
  accept the old one for at least one release.
- The bridge API adds fields freely. Clients must ignore fields they don't know.
  Removing or renaming a field or endpoint is a breaking change; announce it in
  [CHANGELOG.md](CHANGELOG.md) one release before it happens.
- Any change to [cv-semantics.md](cv-semantics.md) regenerates the fixture in the
  same pull request.

## Changing the contract

1. Change the document here first, in its own pull request, with the
   `hydrapy.pin` it was written against. Say what changes for each implementation.
2. Then the implementation pull requests: HydraPy, then this repository's
   `rack/` (which bumps `hydrapy.pin` and regenerates the fixture).
3. Record it in [CHANGELOG.md](CHANGELOG.md).

Anything in this directory that disagrees with the reference implementation is a
bug in one of them. File it against this repository either way.
